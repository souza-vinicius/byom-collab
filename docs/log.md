# Update Log

## 2026-11-24
- **Fix**: o proxy decidia o prazo pelo caminho errado. `FIRST_BYTE_DEADLINE_S = 60` valia para **toda** requisição, mas em non-stream os headers só chegam no fim (`worker/gateway.py:_forward_image` faz `await post(...)` e devolve `JSONResponse`): geração de imagem ou chat `stream: false` acima de 60 s virava 503 com o trabalho da GPU já feito. Novo helper puro `proxy._is_stream_request(path, body)` decide **antes** do envio (`/v1/chat/completions` e `/v1/completions` com `"stream": true`; `/v1/images/*` e `/v1/models` sempre non-stream; corpo ilegível cai no prazo longo). Prazos nomeados: 60 s para stream (primeiro byte) e `NONSTREAM_DEADLINE_S = 600` (10 min) para non-stream — o teto real de trabalho continua sendo `max_job_min` no worker. O 503 do prazo passou a ser `type: byom_deadline` com "o gateway não respondeu em Ns (prazo de primeira resposta)", sem culpar o túnel; `byom_tunnel` ficou só para erro de transporte.
- **Fix**: `qwen-image-2.1:q4km` aponta para o arquivo que o repositório publica, `leejet/Qwen-Image-2.1-GGUF/qwen_image_2.1-Q4_K.gguf` (4.197.494.816 B = 3,91 GiB) — **não existe** Q4_K_M (conferido na API do HF em 2026-11-24). O padrão `*Q4_K_M*` fazia `prepare_runtime.match_file` levantar `ValueError: No model file matches` e abortava o `up` antes de qualquer download. `memory_gib` passou de 12,9 (estimativa da página) para **9,22 GiB**, soma dos bytes publicados: 3,91 (Q4_K) + 4,68 (Qwen3VL-8B-Instruct-Q4_K_M) + 0,63 (VAE bf16) = 9,22 GiB. Com 2 GiB de runtime e 1,0 de folga (12,22 <= 15 GiB utilizáveis) a **T4 volta a ser viável**, então o perfil e o `ProfileContext` voltam para `gpu = "T4"`. `qwen-image-2.1:fp8-int8` deixou de declarar 20,0 GiB sem base: 6,76 (INT8-ConvRot) + 4,68 (encoder) + 0,63 (VAE) = **12,07 GiB**; 12,07 + 2 + 1,0 = 15,07 > 15 mantém a L4. A lista real de arquivos do HF ficou congelada em `tests/fixtures/hf_files.json` (regravada por `scripts/refresh_hf_fixture.py`), então `match_file` é testado sem rede.
- **Fix (segurança)**: o proxy recusa **antes** de montar a URL o que poderia escapar de `/v1/`: segmento `.`/`..`, barra invertida, NUL, `%` (dupla codificação) e qualquer caractere fora de `[A-Za-z0-9._~/-]` → 400 `byom_bad_path`; depois da normalização do `httpx.URL` o caminho tem de continuar em `/v1/` (defesa em profundidade). `GET /v1/../internal/state` chegava ao gateway e rearmava o heartbeat do watchdog. A query string do cliente é preservada; headers de entrada seguem allowlist (`accept`, `openai-beta`, `user-agent`) com `accept-encoding: identity`, sem `host`/`authorization`. `Host` fora de `127.0.0.1[:porta]`/`localhost[:porta]` → 403 `byom_bad_host` (DNS rebinding), em `/v1/*` e em `/__byom/status`.
- **Fix**: cliente do proxy com `httpx.Timeout(connect=5, read=None, write=30, pool=5)` e deadline de 60 s para o primeiro byte (`asyncio.wait_for(client.send(...))`) → 503 `byom_tunnel`; o corpo do stream segue sem read timeout. Todo caminho de saída fecha o `AsyncClient` (inclusive `CancelledError` durante o `send`), sem fechar a resposta que ainda está sendo lida.
- **Fix (segurança)**: `/health`, `/internal/state` e `/internal/begin-shutdown` exigem `X-BYOM-Nonce` igual ao nonce da sessão (`hmac.compare_digest`), porque o forward `ssh -L` faz todo cliente aparecer como loopback; `_is_loopback` fica como defesa secundária. O nonce não é devolvido em nenhum payload de status nem em log. Chamadores atualizados: `tunnel.probe_health`, `Runtime.verify`, `watchdog_supervisor._probe_heartbeat` e `worker/watchdog.py`.
